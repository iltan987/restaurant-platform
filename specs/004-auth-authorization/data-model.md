# Phase 1 Data Model: Authentication & Authorization

All tables live in `packages/db/prisma/schema.prisma` (the API is the sole DB owner). Follow existing repo conventions: `String @id @default(cuid(2))`, `@@map` to snake_case plural, `createdAt`/`updatedAt`. Two groups:

1. **Better Auth identity tables** — generated by `@better-auth/cli generate`, one isolated set per audience instance (D3). Listed here for completeness; their exact columns are owned by the generator, not hand-authored.
2. **Custom membership/invitation domain** — our schema-first models (D5), hand-authored and validated by `@repo/schemas`.

---

## 1. Better Auth identity tables (generated, per instance)

Each instance gets its own four core tables via `modelName` config. Columns are Better Auth's standard core schema (`user`: id, name, email, emailVerified, image, timestamps; `session`: id, userId, token, expiresAt, ipAddress, userAgent; `account`: id, userId, providerId, accountId, password (credential), OAuth tokens; `verification`: id, identifier, value, expiresAt).

| Instance | Tables (`@@map`) |
| --- | --- |
| **admin** | `admin_user`, `admin_session`, `admin_account`, `admin_verification` |
| **dashboard** | `dash_user`, `dash_session`, `dash_account`, `dash_verification` |
| **customer** | `cust_user`, `cust_session`, `cust_account`, `cust_verification` |

- **admin**: only `credential` accounts (email+password); sign-up disabled; exactly one user row (seeded).
- **dashboard**: `credential` accounts; `emailVerified` gates sign-in; rows created on invitation acceptance.
- **customer**: `account` rows may be `google` (OAuth) or `email`/credential-less (passwordless); account-linking collapses same-verified-email rows to one `cust_user`.

> Spec entities **Account**, **Sign-in method / identity link**, **Session**, and **Verification artifact** map onto these generated tables (the verification table backs magic links / OTP codes; our invitation token is separate — see below).

## 2. Custom membership/invitation domain (schema-first)

These reference the **dashboard** instance's user (`dash_user`). They are the basis for all dashboard authorization.

### Enum: `RestaurantRole`
```
OWNER     // full control of the restaurant; can invite/manage members
MANAGER   // operational management (menu, tables, etc.) — exact perms in @repo/schemas permission map
STAFF      // limited day-to-day actions
```
> Final permission catalog per role is defined in `@repo/schemas` (a role→allowed-actions map evaluated server-side), not as DB columns. Start with OWNER + at least one lesser role; refine in tasks.

### Enum: `InvitationStatus`
```
PENDING | ACCEPTED | REVOKED | EXPIRED
```

### Model: `RestaurantMember`  (`@@map("restaurant_members")`)
| Field | Type | Notes |
| --- | --- | --- |
| id | String cuid(2) | PK |
| restaurantId | String | FK → `Restaurant.id`, `onDelete: Cascade` |
| userId | String | references `dash_user.id` (dashboard instance) |
| role | RestaurantRole | |
| createdAt / updatedAt | DateTime | |

- **Unique**: `@@unique([restaurantId, userId])` — one membership per user per restaurant.
- **Index**: `@@index([userId])` (list a user's restaurants), `@@index([restaurantId])`.
- `Restaurant` gains `members RestaurantMember[]`.
- **Invariant (service-enforced)**: every `restaurantId` retains ≥1 `OWNER` at all times (last-owner protection, FR-015).
- **Authorization rule**: a dashboard request for a restaurant MUST match a `RestaurantMember` row for `(restaurantId, session.userId)`; otherwise denied at the data layer (FR-011, FR-016).

### Model: `RestaurantInvitation`  (`@@map("restaurant_invitations")`)
| Field | Type | Notes |
| --- | --- | --- |
| id | String cuid(2) | PK |
| restaurantId | String | FK → `Restaurant.id`, `onDelete: Cascade` |
| email | String | invited address (lowercased) |
| role | RestaurantRole | role granted on acceptance |
| status | InvitationStatus | default `PENDING` |
| tokenHash | String | hash of an unguessable single-use token (raw token only in the emailed link/code; never stored plaintext) |
| invitedByUserId | String? | dashboard user (owner invites) or null/system for admin-issued |
| invitedByAdmin | Boolean | default `false`; true when issued by the platform admin |
| expiresAt | DateTime | bounded TTL (FR-006) |
| acceptedAt | DateTime? | set on acceptance |
| createdAt / updatedAt | DateTime | |

- **Index**: `@@index([restaurantId])`, `@@index([email])`.
- **Partial-uniqueness (service-enforced)**: at most one `PENDING` invitation per `(restaurantId, email)`; re-invite cancels the prior pending one.
- **State transitions**:
  - `PENDING → ACCEPTED` (recipient verifies email via link/code, sets password if no account, member row created).
  - `PENDING → REVOKED` (inviter/admin cancels).
  - `PENDING → EXPIRED` (TTL elapses; lazily on read or via cleanup).
  - Terminal states reject re-use (FR-008, FR-025, SC-005).

> Spec entities **Invitation** → `RestaurantInvitation`; **Restaurant membership** → `RestaurantMember`; **Role / permission set** → `RestaurantRole` enum + `@repo/schemas` permission map.

---

## Identity ↔ domain boundary

- A `RestaurantMember.userId` / `RestaurantInvitation` resolves against the **dashboard** identity instance only. Admin and customer identities are separate (no FK to them).
- The same email may exist as a `cust_user` (diner) and a `dash_user` (staff) simultaneously and independently — they share nothing (FR-021).
- `PrismaService` gains delegates for `restaurantMember` and `restaurantInvitation`, plus the generated Better Auth model delegates as needed by the auth layer.

---

## Validation rules (enforced in `@repo/schemas` + services)

- Email normalized/validated before invitation creation and before membership lookups.
- Role must be a member of `RestaurantRole`; granting `OWNER` via owner-invite is allowed but the last-owner invariant still governs removals/demotions.
- Invitation token: unguessable, single-use, time-limited; compared by hash; invalidated on accept/revoke/expire.
- All restaurant-scoped reads/writes carry the resolved `restaurantId` from membership, never from client-supplied identifiers alone.
